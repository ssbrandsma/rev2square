## Findings and immediate improvements

Priorities: P1 = core workflow blocker; P2 = functional/usability issue; P3 = polish or broader improvement. No new P0, proven security breach, or data-loss incident was observed in this second audit.

### R2S2-B01 — P2 confirmed defect — A task claim can be stored without any task

**Steps:**

1. Use a Published test project with zero contributor tasks.
2. As a separate contributor, open its /contribute form.
3. Select **Claim task** under I want to.
4. Leave Related task at **General help — no specific task**.
5. Enter a valid test message and click Send offer.
6. Sign in as project maintainer and inspect /offers.

**Expected:** a claim requires an eligible task belonging to this project. If no tasks exist, the UI should offer general help and explain that no tasks are available to claim.

**Actual:** submission redirected to the project page. Maintainer view contained a Pending **Claim task** entry with the submitted message and no associated task. This was then declined.

**Reproducibility:** one complete cross-account reproduction, including persistence in maintainer view. Not merely a client-side observation.

**Acceptance criteria:**

- Require a task when type is Claim task, in both UI and server validation.
- Validate task ownership, existence, visibility, and eligibility for claiming.
- Make the optional task label conditional on offer type; it must not say optional for a required task claim.
- Invalid claims create no offer and preserve the entered message with an actionable error.
- Define the relationship between request, approval, and assignment. A pending claim must not silently count as an approved assignment.

**Regression tests:** no task, nonexistent task, another project's task, closed task, deleted task, already assigned task, valid task; switching between Offer help and Claim task; two simultaneous valid claims; repeated submission. Use fixtures for cases not exercised live.

### R2S2-B02 — P2 confirmed discoverability gap — General help exists but cannot be reached from an empty project

**Steps:** view the Published test project as a contributor; inspect Project story, Roadmap, Help wanted, and sidebar. Then open its known /contribute route directly.

**Expected:** a project in Team building with no tasks offers a clear general-help action.

**Actual:** project page showed **No contributor tasks yet.** with no contribution link. The direct route worked and offered **General help — no specific task**. The route pattern was already known from the previous inspection of a task contribution link; an ordinary visitor would have to discover or guess it.

**Reproducibility:** observed before contribution and after submitting offers; direct form verified with the second account.

**Acceptance criteria:** add an Offer help / Join this revival entry point for eligible projects, independent of task existence; anonymous users return to the intended action after authentication; avoid inviting unavailable actions on Draft/Archived projects; show helpful state for existing applicants.

**Regression tests:** no tasks, open tasks, all tasks closed, anonymous user, contributor, maintainer, Draft, Active, Paused, Seeking maintainer, and Archived.

### R2S2-B03 — P2 confirmed UX gap — Contributors cannot find their own application status

**Steps:** contributor submits general help and taskless claim; maintainer accepts the general offer and declines the claim; contributor signs in again and visits Dashboard.

**Expected:** contributors can find their submissions, current decisions, and an appropriate next step.

**Actual:** dashboard still displayed **My revival projects**, **No projects yet**, and **Start a revival**. No submitted-offer or decision list was visible. The maintainer's offer list correctly showed the decisions, but is forbidden to the contributor. Submission returned to the project page without a persistent receipt in the captured DOM snapshots; a transient visual notification was not separately ruled out. Email delivery was not inspected.

**Reproducibility:** dashboard checked before and after maintainer decisions, with a fresh login after acceptance.

**Acceptance criteria:**

- Add a contributor-facing My contributions / Applications area with project, request type, task if applicable, submitted date, status, and next step.
- Show a durable success receipt and prevent accidental duplicate submissions.
- Give contributors access to their own record, not other contributors' private messages or maintainer-only lists.
- Define how an applicant sees their own application when the project becomes Draft, Archived, or otherwise unavailable. Preserve privacy of project content and other users.
- Provide a minimal follow-up path for Accepted and a clear explanation for Declined; do not grant maintainer privileges by accepting an offer.

**Regression tests:** Pending → Accepted/Declined, refresh/new session, multiple projects, no owned projects, own-vs-other record access, project unpublication, withdrawal where implemented, and duplicate submit.

### R2S2-B04 — P2 product-policy gap — Archived project still accepts new offers

**Steps:** maintainer sets the Published test project to Archived; contributor opens /contribute directly and sends a new general help offer; maintainer opens /offers.

**Expected:** lifecycle rules explain whether an archive is read-only. Recommended default: reject new offers/claims while Archived, while retaining historical project and decision records. Reopening should be deliberate.

**Actual:** form remained fully actionable and a new offer was persisted as Pending while the project displayed Archived. Maintainer verification confirmed storage. It was subsequently declined.

**Reproducibility:** one complete cross-account reproduction. Whether continued applications are intentionally allowed is not documented in the inspected UI; treat this as a rule-definition gap until code/product intent is reviewed.

**Acceptance criteria:** document and enforce a state/action matrix on both read and mutation paths. At minimum, explicitly define Draft, Active, Paused, Seeking maintainer, and Archived behavior for general offers, claims, task updates, and source updates. If archive applications are intentionally allowed, label that exception and provide a reason rather than leaving the status ambiguous.

**Regression tests:** all lifecycle states × anonymous/contributor/maintainer; stale form opened before archiving; direct requests; reactivation; no loss of existing offers or decisions.

### R2S2-B05 — P3 confirmed UX gap — Discovery filters are lost on refresh and cannot be shared

**Steps:** /projects → search `Community Workflow` → select Team building and Seeking maintainer → wait for nonmatching cards to disappear → inspect URL → reload.

**Expected:** a discovery state can survive reload and be linked/bookmarked.

**Actual:** filters produced the correct result, but URL remained `https://rev2square.com/projects`. Reload cleared the search and restored both filters to All values.

**Reproducibility:** one complete combined-filter/reload test. Filtering itself worked; asynchronous intermediate snapshots were not counted as a bug.

**Acceptance criteria:** encode supported search/filter/sort state in validated query parameters; restore it on reload/back/forward; add clear-all behavior and result count; do not include private data in public URLs.

**Regression tests:** each filter alone, combined filters, empty results, invalid query values, URL sharing, reload, navigation to a project and back, and rapid typing without stale result replacement.

### R2S2-B06 — P3 product-policy gap — Newly published empty/archived projects become homepage features

**Steps:** publish the empty QA project; visit Home; later set the same project to Archived and visit Home again.

**Expected:** Featured revival projects follows a defined eligibility/selection policy aligned with the adjacent Real devices, real investigations heading.

**Actual:** the fixture appeared in the two-card featured area immediately after publication, despite no linked device, evidence, or tasks. It remained featured while Archived. One existing project was consequently no longer in that two-card area. The underlying selection query was not inspected; do not assert the exact sorting implementation.

**Reproducibility:** observed after publication and again after archiving.

**Acceptance criteria:** define curated features or explicit automatic eligibility; exclude Draft, normally exclude Archived, and avoid equating Published with featured. Allow legitimate early-stage projects in general discovery without manufacturing evidence requirements. If the intention is simply newest projects, label that section honestly rather than implying curation.

**Regression tests:** new Published project, missing device/evidence, Archived, Draft, reactivated project, selected/unselected features, and ordering ties. Do not hardcode the test-project name as the fix.

### R2S2-U01 — P3 usability improvement — Make counters and account context unambiguous

## Prioritized feature plan

Implement small, complete workflows. Reuse existing models/routes and expose already-built capabilities before creating parallel systems. The following are feature proposals or gaps, not eight additional proven bugs.

### R2S2-F01 — Next, high value — Evidence sources and owner observations beyond one repository

**Reason:** the stated methodology includes documentation and owner observations, but the inspected evidence interface only accepts a GitHub repository URL. Community research should continue during GitHub/API outages.

**Minimum scope:**

- Add evidence from a documentation URL, a manually entered observation, and a supported document/log upload. Integrate the ZIP fallback from the previous prompt rather than implementing another importer.
- Record source type, title, origin, author/observer where appropriate, retrieval/observation date, hardware/firmware conditions, and visibility. Distinguish source statements, observations, inferences, and unverified hypotheses.
- Keep immutable revisions or history. An edited observation must not silently change evidence behind an earlier analysis.
- Support multiple sources per project and cross-reference findings to their precise evidence revision.
- For external URL retrieval, bound redirects, sizes, and allowed destinations; protect internal network resources. Treat imported text as untrusted data and never execute it.
- Provide human review and redaction for uploaded logs; warn against including credentials or personal data without blocking ordinary documentation work.

**Acceptance criteria:** a maintainer adds an owner observation and a document without GitHub access; both appear in the evidence list with provenance and review status; AI can explicitly select them when supported; editing creates a traceable revision.

**Tests:** source creation/edit/revision, duplicate detection, unauthorized access, private-to-public review, failed fetch, unsupported file, oversized content, malicious URLs/redirects, unsafe archive fixtures, and citations to historical versions.

### R2S2-F02 — Next, high value — Human-authored milestones and task management independent of AI

**Reason:** Team building should be useful before an AI run. Seeded projects demonstrate task display, but no create/edit controls were discoverable for the audit project.

**Minimum scope:**

- Let authorized maintainers create/edit/order milestones and tasks manually.
- Task fields: title, description, milestone, required skills, hardware needs, definition of done, evidence/test requirements, status, and assignee(s) according to an explicit assignment policy.
- Use a small understandable status set such as Open, In progress, Blocked, Ready for verification, Verified complete. Keep assignment requests distinct from actual assignments.
- Mark provenance as Human authored or AI drafted; approving AI suggestions should feed the same models without duplication.
- Link offers to tasks and offer review to the assignment workflow. Record who changed a status and why.
- Prevent task text that merely claims success from automatically becoming a verified result.

**Acceptance criteria:** create a project with no repository → add a milestone and task → contributor requests assignment → maintainer approves → contributor submits work → verifier records completion. The entire human workflow remains usable with AI disabled.

**Tests:** task CRUD and ordering, permissions, assignment races, invalid cross-project references, blocked/reopened tasks, repeated approval, AI-draft promotion, and preserving references when a task is retired.

### R2S2-F03 — Next, high value — Structured hardware tests and verified outcomes

**Reason:** verified outcomes are central to the public methodology, but no structured test report workflow was discoverable. This is essential product completion, not a finding that seeded project claims are false.

**Minimum scope:**

- Define experiments/test cases with preconditions, steps, expected results, risks, and rollback instructions where relevant.
- Record hardware model/revision, firmware version, software/repository commit, environment, performed date, actual result, and supporting evidence/logs. Keep serial numbers/private network details optional and redactable.
- Separate Passed, Failed, Inconclusive, and Not tested from independent Verified status.
- Let a maintainer/verifier review reports with a recorded decision and rationale. A single-device pass must not imply universal model compatibility.
- Show a compact compatibility matrix per supported hardware/firmware combination, including failures and uncertainty.
- Link verified tests to tasks, milestones, and published claims; invalidate or flag claims if their conditions change.

**Acceptance criteria:** submit two reports on different revisions, including one failure; review them; display accurate per-revision outcomes; no AI output or documentation claim can bypass verification requirements.

**Tests:** required conditions, file attachments, permission checks, failed/inconclusive results, conflicting reports, review history, version changes, redaction, and preventing accidental universal success claims.

### R2S2-F04 — Next — Complete the contribution conversation and decision workflow

**Reason:** accepting help currently updates maintainer status, but the contributor journey lacks discoverable continuity.

**Minimum scope:** implement R2S2-B03, plus a small private discussion on an application, optional decision reason, withdrawal, and deliberate reopen/reconsider actions with history. Add an in-app inbox for meaningful events; email is optional and should respect explicit preferences. Do not default to sending repeated mail.

**Acceptance criteria:** contributor can see their offer, maintainer decision, relevant follow-up, and next action; maintainer can request clarification; notifications link to an authorized view. No global real-time chat system is required.

**Tests:** message visibility, own-vs-other applications, duplicate event delivery, decision reversal history, withdrawn applications, and Draft/Archived projects.

### R2S2-F05 — Next — Explicit team roles and maintainer succession

**Reason:** Seeking maintainer currently changes a badge, not a discoverable recruitment/handover workflow. Accepting general help correctly did not grant management privileges; preserve that boundary.

**Minimum scope:**

- Show a basic project team and roles, distinguishing owner/maintainer, contributor, and verifier where needed.
- Offer a clear Apply to maintain action when Seeking maintainer; keep applications separate from normal task claims.
- Implement deliberate invitations and acceptance, least-privilege roles, revocation, and an audit trail.
- Protect against leaving a project without an owner/maintainer by accident. Do not transfer ownership or sensitive access automatically when a general offer is accepted.

**Acceptance criteria:** a qualified test user applies to maintain; an authorized owner reviews it; the invitation is explicitly accepted before access changes. Verify the new role and revoke it safely in an isolated environment.

**Tests:** role matrix, invitation expiry/reuse, wrong-account acceptance, last-maintainer protection, revocation, and no privilege change from ordinary offer acceptance.

### R2S2-F06 — Later — Task discovery and minimal contributor profiles

**Reason:** Find a task currently opens the project list; users must inspect projects one by one. Skills and hardware needs are already displayed on seeded tasks.

**Minimum scope:** add a task directory filtered by skill, hardware requirement, status, and project; link Home's task call to action to it. Add an optional contributor profile with display name, skills, broad availability, and hardware they choose to list. Do not require private contact details or publish availability/location by default.

**Acceptance criteria:** a user finds an open documentation task without hardware, opens it, and applies; filters survive shared URLs; closed/private tasks are excluded appropriately.

**Tests:** permission-aware search, combinations, pagination, stale task state, no-results suggestions, public/private profile fields, and ownership of profile edits.

### R2S2-F07 — Later — Revival knowledge export and release guidance

**Reason:** verified knowledge should remain portable and useful after an individual maintainer leaves. This is a proposed extension, not a publicly confirmed commitment.

**Minimum scope:** export a project investigation as Markdown/JSON with source URLs, revisions, uncertainty, roadmap, and verified test references. Provide a reviewed owner-facing setup guide and compatibility notes; distinguish planned steps from tested ones. Reference releases/artifacts without automatically executing or installing them.

**Acceptance criteria:** export/import or export review preserves identifiers/provenance and excludes private offers, credentials, and private attachments. Published setup instructions cite verifying tests and list known failures/rollback guidance.

**Tests:** private-data exclusion, broken source links, historical revisions, failed export, reproducibility of referenced commits, and guides with mixed verified/unverified steps.

### R2S2-F08 — Later — Publication readiness, moderation, and project history

**Reason:** the audit project could become both Published and Featured with no device/evidence. Early-stage projects should remain possible, while public status and substantive claims need clarity.

**Minimum scope:**

- Add a short publication checklist and preview: project purpose, device description or explicit uncertainty, maintainer identity, source/claim status, and available next steps.
- Keep early research publishing possible; do not force a successful AI run as a prerequisite.
- Separate published visibility, lifecycle state, evidence verification, and featured selection.
- Add a small activity history for important project/source/task/review decisions, plus report-content and maintainer moderation workflows if opening to a broad audience.
- Make account identity/profile and basic privacy information discoverable. Email verification/anti-abuse policy should be a deliberate launch decision; the owner's current no-verification setup was intentional and is not an audit defect.

**Acceptance criteria:** preview and publish a legitimate early-stage fixture without suggesting it is verified; archive/unpublish it without losing history; configure featured selection according to R2S2-B06; report a test item through a controlled moderation path.

**Tests:** visibility transitions, draft privacy, cache invalidation, lifecycle/action matrix, feature eligibility, history integrity, and safe moderation permissions.
