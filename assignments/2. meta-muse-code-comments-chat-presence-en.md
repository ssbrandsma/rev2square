## Required product structure

Provide three connected but distinct experiences:

1. **Project discussion:** durable, linkable questions, experiences, replies, and announcements that remain useful weeks later.
2. **Live chat:** fast conversations with people currently present, both sitewide and within a project.
3. **Presence:** real, permission-aware information about consenting users currently online, with links to their public profiles.

Discussion posts and chat messages are not automatically technical evidence or verified revival outcomes. Make it easy to turn useful conversation into reviewed evidence or a task without erasing its origin.

## C01 — First delivery: project comments and threaded replies

### Interface

- Add clear project navigation, for example Overview, Discussion, Updates, and Chat. Use counts only for actual records. Existing Evidence/Roadmap/Tasks navigation must remain discoverable; adapt to the current information architecture rather than introducing conflicting menus.
- Discussion shows an honest empty state and an inviting composer for signed-in eligible users. Anonymous users can read public discussions and see a sign-in action that returns to the intended project/composer.
- A post displays avatar or initials, display name linked to public profile, contextual role such as Maintainer, timestamp with an exact-time alternative, and Edited where applicable.
- Support one level of threaded replies initially, stable permalinks, pagination/load more, and a defined sort order. Do not build unlimited nesting for the first release.
- Support safe text, links, and readable code snippets. A simple formatting subset is sufficient; sanitize rendered content. Preserve drafts during ordinary validation/reconnect failures.
- Let an author edit their own post and remove it according to a documented policy; preserve reply context with a tombstone where needed. Record moderation actions separately from author edits.
- Provide report, mute-thread, and maintainer moderation controls. Keep conversation welcoming with short participation guidance, as in the supplied example.

### Domain rules

- Public project discussion is readable publicly. Posting requires an authenticated eligible account; there is no financial-backer requirement.
- Draft project discussions are restricted to explicitly authorized project participants. Accepting a general help offer must not silently grant maintainer rights or access to all private records.
- Archived discussions remain readable where visibility allows; default new comments/replies/chat to closed unless an authorized maintainer deliberately reopens conversation. Define Paused and Seeking maintainer rules visibly.
- Unpublishing must remove public access to posts, counts, previews, notification excerpts, and cached results. Check actual mutation/read paths as well as page controls.
- Link task-specific questions to tasks and preserve context without duplicating the same discussion data in multiple places.

### Acceptance criteria

In an isolated test project, user A posts an experience; user B sees and replies; both can return via a stable link after a fresh login; a maintainer can moderate; unrelated users cannot access draft discussions. A failed request preserves the unsent draft and does not claim success.

### Regression tests

Create/read/reply/edit/tombstone, ownership, moderator permissions, Draft/Published/Archived transitions, pagination/order, long text, empty/whitespace content, unsafe markup, malformed links, double submission, and cross-project identifiers. Test anonymous login return and inaccessible parent posts.

## C02 — Required delivery: actual live chat

### Scope

- Provide one discoverable sitewide **Community lounge** and a project-specific room reached from each eligible project's Chat entry.
- A compact chat launcher in the signed-in app can show unread activity and switch rooms. On small screens, use a usable full-page view; do not cover the project content permanently.
- Deliver messages live between two separate signed-in browser sessions without manual refresh. Persist messages so reconnecting participants can catch up. Clearly label send failure, reconnecting, and offline states.
- Show author, avatar/initials, timestamp, contextual role, safe formatting, and unread/new-message separators. Do not auto-scroll a reader away from older messages; offer a New messages action.
- Add typing indicators where reliable; expire them quickly and do not persist them as activity history.
- Keep the first version focused on group conversation. One-to-one direct messages, calls, and large file sharing are not prerequisites for this request.

### Reliability and authorization

- Use the application's existing supported realtime/broadcast stack where possible. Inspect installed dependencies before choosing the transport or a provider. Do not add an unrelated hosted service without explaining the operational tradeoff.
- Authenticate channel subscriptions and recheck access when membership or publication changes. Treat WebSocket/SSE messages and HTTP history endpoints as equally sensitive authorization surfaces.
- Store the message before publishing an event. Use client-generated submission identifiers or equivalent idempotency so retry/reconnect produces one stored message.
- Use server-established ordering/cursors. Recover messages missed during disconnect and avoid duplicates when history and live events overlap.
- Revoke subscriptions on logout, lost membership, or unpublication. Do not broadcast private-room content over a public channel and hide it only in the UI.
- If realtime delivery is unavailable, show that honestly and use an explicit degraded mode if feasible. A mock animation or manual-refresh feed is not a completed live-chat feature.
- Define history retention, moderation/tombstone behavior, rate limits, and maximum message size. Notify users of the practical behavior in product language.

### Acceptance criteria

Two independently authenticated test users in the same allowed room exchange messages live, normally within two seconds in the controlled test environment. Disconnect/reconnect delivers missed messages once. A third unauthorized user receives neither history nor live payloads. If the transport fails, the interface does not falsely claim a live connection.

### Regression tests

Two-session live exchange, concurrent sends, retry, reconnect, event/history overlap, pagination, process restart, token/session expiry, logout, unauthorized channel names, lost membership, project unpublication, slow network, and realtime-service failure. Verify persistence and server records, not only visual bubbles.

## C03 — Required delivery: who is online

### User experience

- Add a sitewide Online now entry with consenting members' avatars/initials and display names linked to public profiles. Add a project-local Here now roster showing eligible users in that room/project context.
- Distinguish Active/Online, Away where supported, and connection failure. A recent historical login is not evidence of current presence.
- Make identity visibility user-controlled through the profile settings from the paired prompt. Suggested initial policy: users explicitly opt in to having their name/avatar listed; other users can still use discussions and chat. Explain the effect clearly.
- A user's public presence must not disclose which private/draft project they are visiting. Project rosters are only available to viewers authorized for that context.
- Do not expose email, IP address, exact location, device identifiers, or browsing trails. Do not invent named guest users. If displaying an aggregate count, label exactly what it counts, such as members sharing presence.
- Deduplicate one account across several tabs/devices. Online status does not mean available to respond immediately.

### Suggested initial semantics to implement and document

- Presence is ephemeral and based on authenticated live connections/heartbeats plus recent activity, not a permanent database flag.
- Suggested heartbeat interval: 30 seconds; stale connection expiry: 90 seconds. Healthy connected users may be shown Away after five minutes without interaction. These defaults are configurable and should be tested with a controlled clock.
- Send only coarse activity signals; do not capture typed text, URLs visited, or detailed interaction telemetry to calculate presence.
- Aggregate connections per user. Closing one of two tabs must not remove the account while the other still provides presence.
- Opting out removes identity from shared presence promptly. Logging out clears that connection; abrupt closure expires automatically. A presence-service outage displays unavailable status rather than zero users or fake stale identities.

### Acceptance criteria

With two independent test users opted in, each can see the other appear and disappear according to documented timing. One account with two tabs appears once. Opt-out takes effect across site/project rosters. An unauthorized observer cannot infer private-room membership. No fake online counts or seeded always-online people are used.

### Regression tests

Join/leave, abrupt disconnect and expiry, two tabs, two devices, one tab closing, idle/away, reconnect, logout, opt-out, anonymous observer, private room authorization, membership revocation, clock skew, multiple app workers, and presence-store outage.

## C04 — Make conversations feed useful collaboration

- Add Follow project and Follow discussion with an in-app notification inbox shared with the profile prompt. Replies and mentions are useful defaults; avoid alerting every member for every chat message.
- Link authors, project members, and consenting online users to the same public-profile system. Roles are derived from actual scoped membership, not free-text badges.
- Let maintainers publish short project Updates that participants can discuss. Keep official updates distinguishable from ordinary comments; record author, publication time, and edits.
- Offer a deliberate **Create evidence from this post** / **Create task from this discussion** action for authorized maintainers. Prefill source permalink and attribution, show a review step, and link the resulting record back to the conversation. Never turn a chat claim into a verified outcome automatically.
- Treat likes/reactions, attachments, advanced topic organization, and direct messages as later enhancements, not substitutes for the requested core functions.

**Acceptance criteria/tests:** notification preferences work; duplicate delivery is deduplicated; only allowed content appears in notification previews; self-actions do not produce unnecessary alerts; promotion to evidence/task preserves origin and review state; deleting/moderating the source does not silently rewrite a historical technical claim.

## Shared operational requirements

- Apply ordinary spam/flood controls, report handling, and moderation to both comments and chat. Explain temporary limits without losing drafts.
- Use the same account restrictions/block policy consistently. Define whether blocked users' posts are hidden only for the blocker or globally moderated; do not conflate these actions.
- Test keyboard use, accessible names, readable timestamps, focus after send/error, and restrained live-region announcements. Do not read an entire busy chat aloud or move focus on incoming messages.
- Render useful conversation history server-side or through a reliable initial fetch; realtime enriches an already usable page.
- Use indexed/cursor-based history and scoped presence channels. Avoid one sitewide database update per heartbeat or N+1 profile queries per message.
- Record operational health and safe diagnostics; never log authentication secrets or full private conversations merely for debugging delivery.
