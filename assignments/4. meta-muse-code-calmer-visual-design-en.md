# Meta Muse Code — Give Rev2Square a calmer, more distinctive visual identity

## Design brief

Refine Rev2Square's look and feel so it feels like a credible, welcoming community for people restoring hardware. The owner finds the current typography and overall presentation too similar to generic AI-generated websites. The desired result is quieter, more human, and more deliberate: clear reading, useful project information, and real people take precedence over promotional styling.

Use the supplied Kickstarter screenshots as visual references for restrained typography, generous spacing, clear navigation, and recognizable author/project identity. Do not copy Kickstarter's branding or claim to use its exact proprietary font. This is a design refinement, not a request to disguise AI-generated research or remove meaningful AI disclosures.

Preserve existing functionality, routes, data, and the work underway on profiles, discussions, chat, presence, evidence, and tasks. Apply a shared visual language across those features rather than redesigning each separately.

## Starting observations and limits

Previously inspected Rev2Square screens use a large dark header/project banner, prominent bold headings, uppercase widely spaced section labels, green actions and status chips, and many rounded bordered containers. The combination can feel like a reusable product template rather than an established research community.

These are subjective design observations, not functional defects. The current font's actual family was not established in the browser audit. Inspect its computed styles, font loading, and existing design tokens before changing it. Do not assert that the current site uses a particular typeface without checking.

## 1. Typography: the highest-priority change

- Replace the current heading/body typography with a quieter humanist sans serif. Start with **Source Sans 3** as a concrete candidate, subject to font availability and license verification. Its purpose here is readable, understated text, not imitation of Kickstarter's exact font.
- Use one primary family for navigation, headings, forms, cards, and body text. Keep a monospace family only for code, hashes, logs, and other technical identifiers.
- Start with body text around 17px with a 1.55–1.65 line height. Use regular body weight, medium navigation, and semibold headings. Avoid routinely using very heavy headings or making all text bold.
- Give project titles a moderate scale: approximately 30–36px on desktop and 26–30px on narrow screens. Hero headings can be somewhat larger where necessary, but should not overwhelm actual content.
- Prefer sentence case for section headings and labels. Remove widespread uppercase, small type, and exaggerated letter spacing. Technical identifiers may retain their necessary casing.
- Set a comfortable reading measure, roughly 65–75 characters for long project stories, research notes, and discussion posts. Keep tables and useful project layouts wider when needed.
- Use a sensible fallback stack and load only needed weights. Confirm font licensing, serve font assets through the project's existing asset approach, and avoid introducing unnecessary external font tracking/dependencies.

**Acceptance criteria:** typography is noticeably calmer on Home, a populated project page, Discussion, Profile, Dashboard, and forms; body text remains comfortable to read; font fallback does not break layout; font changes do not cause text clipping or large layout shifts.

## 2. Layout: use an editorial rhythm and fewer containers

- Let the main content sit on a quiet light background with clear margins. Use spacing, alignment, and occasional thin dividers to define sections.
- Replace repetitive card-within-card layouts with plain sections, lists, and readable rows. Retain a card where it represents an actual independent item, such as a project, task, or evidence source.
- Reduce oversized dark blocks on detail pages. Let the project title, device, short pitch, and useful navigation establish hierarchy without a large promotional banner dominating the first screen.
- Use a stable content grid and spacing scale. Avoid stacking several unrelated label/badge/subtitle rows above the content.
- Keep the useful project sidebar where appropriate, but make it visually lighter than the main story and current work. Collapse it sensibly on smaller screens.
- Make discussion feeds feel like conversations: clear author lines, a comfortable text column, subtle separation, and restrained reply indentation.
- Give profile pages real identity through chosen avatars, bios, and project/work history rather than decorative panels or large invented metrics.

**Acceptance criteria:** users can quickly identify what a project is, its current state, what is known, and how to contribute; content remains easy to scan without surrounding every paragraph with a border.

## 3. Color and surfaces: restrained, functional emphasis

- Use warm white or a very light neutral for primary surfaces, dark neutral body text, and accessible muted secondary text.
- Keep a recognizable Rev2Square green, but use it selectively for the primary action, links, and meaningful accents. Avoid making every badge and decorative detail compete for attention.
- Remove gratuitous gradients, glows, decorative background shapes, glass effects, strong shadows, or animated ornaments if present in the current implementation. Do not introduce them during this redesign.
- Use thin neutral borders, little or no shadow, and modest consistent corner radii. Reserve fully rounded shapes for avatars and appropriate compact controls.
- Maintain genuine semantic distinctions for success, warning, error, and unverified status. Include text/icons where useful; do not rely on color alone.
- Check text, controls, focus indicators, and status colors for accessible contrast. A calmer interface must not become a low-contrast interface.

## 4. Navigation, buttons, and status labels

- Make the main navigation compact, stable, and easy to read. Consider a light header as the default; preserve brand recognition without a heavy full-width dark treatment on every screen.
- Use one clear primary action per section. Render secondary actions as restrained outlined buttons or text links according to importance.
- Reduce oversized pill buttons and button-like badges. Status should read as information, not look like a call to action.
- Show only the few statuses that matter in context, with explanatory text available when needed. Do not hide lifecycle, draft visibility, review status, or uncertainty merely to reduce visual clutter.
- Use consistent small icons only when they improve recognition. Avoid decorative emoji as section headings or mismatched icon styles.
- Use subtle interaction feedback. No unnecessary entrance animations, bouncing notifications, or persistent attention-seeking motion.
- Integrate chat, presence, and notification controls quietly. Incoming messages must not cover the page, steal focus, or create a permanent distraction.

## 5. Language and AI presentation

- Prefer concrete product language such as Project story, Evidence, Current work, Discussion, and Test results.
- Reduce repetitive slogans and promotional filler. Give real projects, useful tasks, and actual people more space on Home.
- Use honest empty states with one useful next action instead of decorative illustrations or inflated claims.
- Keep AI analysis clearly identified where it exists, including draft/review state and source limitations. A more human visual identity must not imply that AI output is human-verified work.
- Do not invent testimonials, activity counts, online users, achievements, or project imagery to make the site appear established.

## 6. Implement a small, reusable visual system

Inspect and update shared typography, color, spacing, radius, border, and component tokens. Avoid page-specific overrides that gradually create competing designs.

Apply the changes to:

1. Home and project discovery.
2. Populated project detail pages and empty/draft project states.
3. Evidence and analysis states, preserving technical readability.
4. Dashboard, offers, and create/edit forms.
5. User profiles and account menu as those features are implemented.
6. Discussion, chat, online presence, and notifications as those features are implemented.

If new features are not yet present, update the reusable components and document their intended styling; do not fabricate working pages or claim those features have been completed.

## Delivery approach

1. Inspect current fonts and shared styles. Summarize the specific sources of the current template-like appearance.
2. Implement one coherent visual direction using Source Sans 3 as the starting candidate. If it is unsuitable, explain a concrete alternative and the reason. Avoid offering a long catalogue of fonts instead of completing the design.
3. Show before/after screenshots of Home, a populated project page, and a representative form/dashboard. Add Profile/Discussion comparisons if implemented.
4. Check the design at representative desktop and mobile widths. Fix overflow, broken wrapping, cramped navigation, and awkward stacked sidebars.
5. Verify core navigation, forms, focus states, validation messages, publication visibility, and status readability still work. Use existing functional tests; add tests only where behavior changes or a real regression risk warrants them.
6. Deliver the shared style/component changes, actual visual checks, any font asset/license notes, and remaining limitations. Keep the result consistent with ongoing community/profile implementation.

## Completion criteria

- The site feels like a focused hardware-revival community rather than a generic AI product landing page.
- The new font, moderate weights, sentence-case labels, quieter surfaces, and reduced container clutter create a visible difference.
- Real content and people carry the identity; decorative styling does not dominate.
- Reading, keyboard navigation, contrast, and mobile usability are preserved or improved.
- No important evidence, uncertainty, AI disclosure, lifecycle state, or permission boundary is lost.
- Existing functionality remains intact, and the shared design works for new community and profile features.
