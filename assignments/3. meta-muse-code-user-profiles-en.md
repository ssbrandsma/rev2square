# Meta Muse Code — Rev2Square user profiles, project participation, and the account menu

## Goal

Create a useful member identity and personal workspace for Rev2Square. People should be able to see who started a revival, who is working on it, what someone has actually contributed, and where their own applications/tasks/conversations stand.

Use the supplied Kickstarter account-menu screenshot as interaction inspiration: avatar, recognizable account identity, useful account actions, and a compact project list. Translate its ideas to Rev2Square rather than copying fundraising language. **Started projects**, **Working on**, and **Contributions** are meaningful here; **Backed projects**, donation totals, and spending-based status are not.

Coordinate with `meta-muse-code-comments-chat-presence-en.md` and the previous community-workflow audit. These specifications must share one user/profile model, one project membership/role model, and one notification/read-state system. Inspect current source and work in progress first; expose and extend existing capabilities rather than creating parallel implementations.

## P01 — Required: recognizable account identity and menu

Provide a signed-in avatar/initials button with the member's display name and an accessible menu. Include:

- View my public profile.
- My workspace: Started projects, Working on, My contributions, and My applications.
- Saved/followed projects.
- Notifications and conversations, using the shared community implementation.
- Edit profile and Account settings.
- Log out.

Show a compact recent-project list in the menu or adjacent workspace panel. Each entry should show project name, optional real project/device image or a clean fallback, contextual role/status, and a link. Keep the list bounded with View all; do not download every project or conversation to open the menu.

The user should immediately recognize which account is signed in. Unread dots/counts must reflect real unread items and be accompanied by accessible text. Do not display fake activity, fabricated avatars, or invented project thumbnails.

**Acceptance criteria:** after sign-in, the member can open their profile and reach their projects/applications in one or two deliberate steps. Opening/closing the menu works with keyboard, focus returns correctly, and logout clears identity/presence. Anonymous header remains appropriate.

**Tests:** logged-in/out states, account switching, initials fallback, long display name, no projects, many projects, unread state, outside click/Escape, keyboard order, and small-screen layout.

## P02 — Required: public profile and a separate private workspace

### Public profile

Use a stable public identifier/handle that does not expose an email address. Show:

- Avatar or initials and display name.
- Optional short bio, skills, relevant public links, broad availability, and hardware/model interests the member chooses to share.
- Public projects started/maintained and current public collaborations.
- Recorded public contributions with meaningful links to tasks, evidence, reviewed tests, documentation, or releases where these records exist.
- Contextual roles and understandable statuses. Project maintainer status is scoped to a project; it is not a global expert certification.

Keep onboarding lightweight. A new member can comment or offer help without completing a long profile questionnaire. Optional fields must have sensible empty states and no fabricated content.

### Private workspace

Show the owner's full operational view separately:

- Owned/maintained projects, including their authorized drafts.
- Current team participation and assigned tasks.
- Submitted offers/claims with Pending, Accepted, Declined, or Withdrawn states where implemented.
- Work awaiting review, blocked tasks, notifications, saved projects, and conversation links.
- Clear next actions rather than only counters.

Do not expose private offers, rejection decisions/reasons, private messages, saved-project lists, account email, or drafts through the public profile by default. A public profile is not a public copy of Dashboard.

**Acceptance criteria:** visiting a member's public profile as another user shows only permitted public information; opening My workspace as that member adds their private records. A contributor with no owned project but an existing application sees useful information rather than No projects yet as the entire experience.

**Tests:** self vs another member vs anonymous viewer, zero contributions, private/draft projects, public/private profile fields, blocked/restricted accounts where supported, pagination, and invalid identifiers.

## P03 — Required: truthful project participation and contribution attribution

Define project relationships explicitly and derive profile lists from those relationships:

| Profile section | Meaning | Must not mean |
|---|---|---|
| Started | Member created the project; retain historical creator attribution if ownership changes | Currently owns all management rights forever |
| Maintaining | Member currently has an authorized maintainer/owner role | Once submitted a help offer |
| Working on | Current explicit project membership or an approved assignment according to the domain rules | Merely viewed, saved, followed, commented on, or applied to a project |
| Contributions | Concrete attributable work records, with their current review/completion status | A raw comment count presented as engineering achievement |
| Applications, private | The member's submitted offers/claims and decisions | Public team membership or completed work |
| Following/saved, private by default | Interest/bookmarks chosen by the member | Contributor status |

An accepted general offer proves that an application was accepted; it does not by itself prove completed work or necessarily create team membership. Inspect and document the existing semantics. If approval should offer a Join project step or membership invitation, implement that explicitly and integrate it with the team workflow. Do not quietly turn accepting help into maintainer access.

Contribution cards should identify the kind of work and link to its source record, for example:

- Documentation task completed and reviewed.
- Evidence/owner observation submitted, with Pending review or Reviewed status.
- Hardware test performed, with Passed/Failed/Inconclusive and separate verification status.
- Code/release contribution with a verifiable linked source where supported.

Failed but useful experiments can be credited as work without claiming the device is fixed. A self-entered external achievement should be labeled Member supplied until verified; do not fabricate GitHub verification or import unrelated activity automatically.

Preserve historical attribution after a member leaves or a task is reopened, while updating current status honestly. Count each logical contribution once. Distinguish current roles from historical participation.

**Acceptance criteria:** a pending applicant is visible only in their own applications; approved membership appears in Working on; completing/reviewing a task creates the appropriate contribution; reversing/reopening work updates status without erasing provenance or inventing achievement counts.

**Tests:** Pending/Accepted/Declined/Withdrawn, invitation not yet accepted, assigned/unassigned task, completed/reopened task, duplicate approval, contribution review reversal, membership removal, ownership transfer, and several records referencing one contribution.

## P04 — Required: useful project cards and navigation

- Provide Started, Maintaining/Working on, and Contributions tabs or sections with clear counts and empty states. Use language appropriate to the actual member's relationships; avoid redundant empty tabs where a simpler layout is clearer.
- Cards show title, pitch/device where available, project lifecycle, personal role, and relevant progress such as an assigned task. Use truthful aggregate status; task completion is not automatically verified hardware support.
- Link from project team lists, discussion/chat authors, accepted participants where appropriate, and consenting online rosters to the same member profile.
- Public project counts must match the visible public list; private draft counts must not leak through badges, pagination totals, search snippets, or image metadata.
- Retain useful public history for Archived projects with a clear Archived label. An unpublished project stops appearing in other users' public profile views immediately according to the cache policy.

**Acceptance criteria/tests:** profile lists and counts agree for every viewer; a project's publication/membership change updates all relevant views; no private project title or draft existence leaks through counters; links remain valid after supported profile/name changes.

## P05 — Required: edit profile, identity, and presence preferences

Provide profile editing for display name, optional handle, bio, avatar, skills, and relevant links. Use existing account identity as the starting point; migrate older accounts to a usable profile without requiring re-registration.

- Validate lengths, duplicate/reserved handles, and allowed link formats. Render bio safely and avoid allowing profile links to execute script content.
- Avatar upload should use bounded image validation/resizing, remove unnecessary embedded metadata, and provide a delete/reset-to-initials option. Do not use the real people in the supplied screenshots as seed avatars.
- Preserve stable author attribution through display-name changes. Define handle-change behavior without breaking shared links unnecessarily.
- Keep authentication/email/password settings separate from public-profile fields. Never put account email or other private identity data into public profile responses.
- Add the presence preference required by the community prompt: whether name/avatar appears in online rosters, clear explanation, and consistent behavior across site/project chat. Presence opt-out must not prevent use of ordinary community functions.
- Do not require exact location or public contact details. Optional broad availability and hardware interests are self-described and should be labeled accordingly.

**Acceptance criteria:** existing account can personalize its profile, preview public information, and change presence visibility without altering privileges. A different user cannot edit it through either UI or direct requests.

**Tests:** self-only mutation, unsafe biography, duplicate/reserved handle, display-name update across author cards, malformed/oversized image, invalid URLs, reset avatar, historical links, opt-out propagation, and public/private API serialization.

## P06 — Required: saved projects, activity, and notifications

- Implement a simple Save project/bookmark function if not already present. Keep private by default, separate from Following notifications and Working on membership.
- Provide a meaningful private activity feed: application decisions, assigned/reopened tasks, replies/mentions, requested reviews, and followed project updates. Reuse the community prompt's inbox; do not build a second event/read-state table for profile notifications.
- Group and deduplicate events; do not generate a notification storm from chat messages or the user's own actions.
- Use notification preferences and working unread/read state. Every notification deep link must recheck access; if content becomes private/unavailable, show a neutral authorized explanation without leaking old snippets.
- A public contribution timeline may show selected public work, but not the member's browsing history, login times, pending offers, or full private inbox.
- A Recommended for you menu item should be added only when an actual recommendation experience exists. A blank or fabricated recommender is worse than omitting the item.

**Acceptance criteria/tests:** save/un-save idempotently; a followed update or received reply produces one meaningful notification; marking read updates the same badge across profile/menu/chat; private records remain private after publication or membership changes.

## Visual direction from the reference

Use the reference to achieve an immediate sense of belonging: avatar in the header, a compact account panel with recent project relationships, and visible credit for concrete work. Reuse Rev2Square's colors, type, spacing, and components. Prefer honest empty states and initials over decorative fake metrics.

The menu must remain useful for someone who has started no project but is working on one. Profile cards should celebrate research, documentation, testing, and maintenance alongside code. Do not add donation-based ranks, speculative reputation scores, or competitive leaderboards as a substitute for attributable work.

## Implementation and delivery sequence

1. Inventory existing users, profiles, offers, memberships, assignments, activity, media handling, and notification code. Identify what already exists and avoid conflicting work from earlier prompts.
2. Implement the menu, public profile, private workspace, and project relationship semantics. Add truthful empty states for data not yet supported.
3. Wire contribution attribution to actual records and review transitions. Coordinate manual evidence/tasks/test reports with the earlier community roadmap; do not invent completed contributions merely to populate a page.
4. Add editing, saved/followed distinctions, shared inbox, and presence settings; connect discussion/chat authors and rosters to profiles.
5. Test with at least two independently authenticated accounts and projects in different publication states. Reuse dedicated nonproduction fixtures; do not expose the live audit drafts to demonstrate populated public profiles.
6. Deliver a short feature inventory, actual tests, screenshots of a populated public profile, private workspace, and menu, migration notes for existing accounts, and explicit remaining limitations.

## Demonstration and regression checklist

Demonstrate user A creating a project, user B applying, explicit membership/assignment, recorded work, and review. Check A's Started/Maintaining and B's Working on/Contributions sections. Repeat as an unrelated viewer and confirm that pending applications, private messages, and drafts never appear. Change a project to Draft and confirm public profile cards/counts and notifications follow the access rules. Remove B from the team and show the difference between current membership and historical work credit.

Also test keyboard/mobile navigation, account switching, long text, zero/many projects, pagination, duplicate event handling, stale caches, profile edits, membership revocation, reopened work, and presence opt-out. No real credential change, ownership transfer, or deletion should be performed against existing community users/projects just for validation.
